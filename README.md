# React Unit Test Toolkit

**Targeted unit test generation for React/TypeScript coding assistants.** This project ships a local MCP server and an optional Cline-compatible skill. It helps an AI coding assistant choose a **selected, newly added, or modified component or hook**, explore only the relevant local dependencies, plan source-grounded scenarios, validate a generated test, and run focused Vitest checks.

The MCP server **does not call an LLM, write test code, or change production files**. Test scenarios and code are generated by the coding assistant and its configured model. Nothing in the toolkit requires a separate model API key.

> **Scope:** Vite + React + TypeScript + Vitest is the demonstrated setup. Jest-only, Next.js Server Components, and complex monorepos are not automatically supported.

## Workflow

```text
User picks a component OR Git lists new/changed candidates
                       │
           Code analyzer (TypeScript AST)
                       │
       Limited dependency graph (1–2 hops)
                       │
    Coding assistant plans code-specific scenarios
                       │
       Coding assistant creates/updates ONE test
                       │
    Static validation → Vitest selected test → report
                       │
  Optional: Vitest related regression tests + coverage
```

**This is not a whole-repository test generator.** Scanning local module imports for the graph does not mean the server sends the full source tree to the model or generates tests for every module. The dependency tool returns at most 12 short source excerpts for the selected target's reachable imports; callers are reported as file paths only. Git changes are used to suggest **candidates**, not to silently generate tests for everything.

## MCP tools

| MCP tool | Function |
| --- | --- |
| `inspect_project` | Inspect test dependencies, scripts, and configuration |
| `analyze_react_file` | Analyze one selected React/TypeScript source using AST |
| `get_related_context` | Find a selected module's local import graph, with up to 2 dependency hops and short source excerpts |
| `get_changed_components` | List added/modified/renamed component and hook candidates using Git; separate changed utility modules |
| `get_affected_components` | Find reverse-import component/hook candidates affected by a change |
| `validate_test` | Check test syntax, direct target import and basic assertions (heuristic) |
| `run_unit_test` | Run exactly one existing Vitest test file with a timeout |
| `run_related_tests` | Run Vitest's related tests for a specified source file, not the full suite |
| `get_test_coverage` | Read an existing `coverage/coverage-final.json` file for a source |

**Git behavior:** `get_changed_components` defaults to changes relative to `HEAD` (tracked edits and untracked files). Pass `baseRef: "HEAD~1"` to compare to the previous commit, if it exists; the reference can also be a commit SHA. Rename detection is best-effort, like Git itself. Deletions and test files are not automatically test-generation targets.

**Relations:** Static relative imports and TypeScript `paths` aliases are resolved when possible. Reverse imports help assess impact. Dynamic runtime dependencies may not be discovered. Source scans are bounded (up to 800 files / 6,000 directory entries) and skip symlinks and generated folders. A too-large codebase may produce an incomplete graph with a warning.

## Requirements

- Node.js 22+ and npm, plus Git for change discovery.
- A **trusted** React project with Vitest installed locally. React Testing Library is recommended for component tests.
- An MCP-compatible coding assistant. Cline uses the included skill directory.

## Installation

Clone this repo, then:

```bash
npm install
npm run build
npm test
```

For the included example app:

```bash
npm install --prefix examples/demo-react --legacy-peer-deps
npm run test:demo
npm run test:mcp
npm run coverage:demo
```

The demo install uses `--legacy-peer-deps` as a workaround for a documented npm 10 peer-resolution issue affecting some Vitest 4 dependency trees. It is also configured in `examples/demo-react/.npmrc`. For a real application, follow its existing dependency lockfile and package manager; do not blindly change its install policy.

### Connect your MCP client

Configure a local `stdio` MCP server. Adapt [`templates/cline-mcp-settings.json`](templates/cline-mcp-settings.json) to your filesystem:

```json
{
  "mcpServers": {
    "react-unit-testing": {
      "command": "node",
      "args": ["/absolute/path/react-unit-test-toolkit/dist/server.js"],
      "env": { "REACT_TEST_ALLOWED_ROOT": "/absolute/path/to/your-react-project" },
      "disabled": false,
      "autoApprove": []
    }
  }
}
```

`REACT_TEST_ALLOWED_ROOT` **must point to exactly one trusted project**, and tool paths are relative to that root. Change the environment variable and restart the MCP server to switch projects. `disabled` and `autoApprove` are Cline-specific settings; other clients may use different configuration keys. No hosting or external service is needed for `stdio`.

### Install the skill

Copy [`.cline/skills/react-unit-testing/SKILL.md`](.cline/skills/react-unit-testing/SKILL.md) into the target project at `.cline/skills/react-unit-testing/SKILL.md`, or adapt the content to your coding assistant's instruction system.

Example requests:

> Analyze `src/components/LoginForm.tsx` and its relevant dependencies. Plan and implement behavior-driven Vitest/RTL tests for **that component only**. Validate and ask permission to run them.

> Find newly added React components from Git changes. Show me the candidates first; then create tests for the ones I select.

> Determine which components could be affected by `src/hooks/useAuth.ts` and recommend which focused tests to rerun.

## Security and limitations

- MCP tools inspect project files only inside the configured root. They do not install packages, change production code, or expose a general shell tool.
- The graph index does **not** follow symbolic links, and source excerpts have size and count limits.
- `run_unit_test` and `run_related_tests` execute real project code. **They are not sandboxed** by a timeout; explicitly approve calls and use isolated environments for untrusted projects.
- Test passing means the code executed, not that assertions are useful or requirements are complete. Static validation is heuristic.
- The MCP server does not use an external model API. Your coding assistant, package manager, project tests, and other tools may have their own network behavior. Review them separately.
